# @askgina/os-signer

The signer holds every wallet key of a deployment and decides, on its own, whether to sign. It is a small HTTP service on internal networks that only the control plane and the keyless `approve` service (which serves the confirmation page) can reach.

The control plane can ask the signer for things. It cannot make it sign. Every operation that adds authority (signing a transaction, changing a policy, adding an approver, lowering or raising a threshold, resuming a paused workspace) must carry passkey assertions over a statement of that exact operation (an _envelope_). The signer recomputes the envelope's digest, checks each assertion against its own registry of approvers, and acts at most once per approval and per nonce.

The contract is [`packages/protocol/src/signer/api.ts`](../../packages/protocol/src/signer/api.ts). The design and its reasons are in [the ExecPlan](../../specs/agent-workspaces-v0.1.md), Milestone 2.

## What it trusts

- **Its own SQLite file** (`$SIGNER_DATA_DIR/signer.sqlite`): workspaces, approvers, wallet policies with their hash chain, used nonces, signed transactions, the spend ledger, the decision log, the restore fence, open confirmations with the assertions made on them, the possession challenges of approver changes (table `possession_challenges`), mandates with their grantors and every use (tables `mandates`, `mandate_grantors`, `mandate_uses`), and every attempt after a first signature (table `signature_attempts`). Its schema version is `PRAGMA user_version`, now 6 (version 5 added the three mandate tables, version 6 `signature_attempts`); the signer migrates it in one transaction when it opens the file, and refuses to open a file written by a newer signer (`SchemaTooNewError`, logged as `schema_too_new`).
- **Its vault** (`$SIGNER_DATA_DIR/vault`): an [Open Wallet Standard](https://github.com/open-wallet-standard/core) key store, one wallet with its own mnemonic per wallet id. OWS is used only to keep keys encrypted and sign; it enforces nothing. The signer builds every transaction itself from the approved intent (`to`, `value`, `data`, the chain; ERC-20 calldata is encoded here), so it never signs bytes a caller handed it.
- **Two request-signing secrets**, one per scope. The control plane's (`SIGNER_HMAC_SECRET_FILE`) proves a request came from the control plane within the last minute; it reaches every route except the four confirm routes. The `approve` service's (`SIGNER_CONFIRM_SECRET_FILE`) reaches only those four, so a compromised confirmation page cannot sign, apply or read anything else. Pausing a workspace, revoking an approval and revoking a mandate need only the control plane's secret, because they only remove authority.
- **The relying party** (`WEBAUTHN_RP_ID`, `SIGNER_APPROVAL_ORIGIN`). An assertion counts only when the browser made it on the confirmation page: at `SIGNER_APPROVAL_ORIGIN` exactly, top-level (not in a frame: no `crossOrigin: true`, no `topOrigin`), as a `webauthn.get`, under `WEBAUTHN_RP_ID`. The same rule holds when the signer signs, when it applies an admin change, and when it accepts an assertion on a confirmation route. An assertion made on any page the control plane serves is refused with `assertion_invalid`. No setting widens this: the earlier `WEBAUTHN_ORIGINS`, which let the control plane's own page approve, was removed (`specs/trusted-display.md`, milestone 3).
- **The operator's label files** (`SIGNER_CHAINS_FILE`, `SIGNER_ASSETS_FILE`): chain names, native coins, token symbols and decimals shown on the confirmation page. They change what a person reads, never what is signed.

It does **not** trust the control plane's database, its idea of who is an approver, or anything it says about a challenge. A compromised control plane can withhold requests, mislead a person in its own pages, and link them to the confirmation page of another request, but the page shows what the signer holds and only an approval made there counts. A compromised `approve` service, or the proxy in front of it, can show a false view on that page and relay an approval over another digest: for a payment the per-wallet caps bound what that can cost; a sweep is bounded by where it may go; a misled change of policy or approvers is not bounded (see "Limits" in [`docs/threat-model.md`](../../docs/threat-model.md)).

## Signing

`POST /v1/sign`, in this order; every refusal is returned with its code, and every refusal after step 1 for a workspace the signer knows is recorded in that workspace's decision log (see "Decision log"):

1. Request signature and schema.
2. Idempotency: the same approval id with the same envelope returns the stored transaction; a different envelope is `conflict`.
3. The restore fence (see "Restoring"): an envelope issued before the fence plus 30 seconds is `envelope_fenced`.
4. The envelope is `approve-intent` and matches the intent's workspace, wallet, agent and chain; `intentHash(intent)` equals the envelope's.
5. The workspace is not paused; the approval is not revoked. Step 2 comes first on purpose: a repeat of an approval that was already signed returns the stored transaction even while the workspace is paused. Pausing stops new signatures; it does not recall one that exists.
6. The wallet has a policy and its hash equals the envelope's.
7. Passkey assertions from the signer's own approvers, at the policy's threshold, within the policy's lifetime (and `SIGNER_MAX_INTENT_TTL_SECONDS`).
8. `gas × maxFeePerGas ≤ maxFeeWei` and `maxPriorityFeePerGas ≤ maxFeePerGas`.
9. One SQLite transaction with no `await` inside: the fence again, the envelope nonce is unused, the policy allows the intent against the last 24 hours of signed spends, the vault's signature recovers to the wallet's address over exactly the transaction the signer built, then the nonce, the spend, the signed transaction and the decision are stored together.

`POST /v1/wallets/:walletId/sweep` signs a person's `sweep-wallet` approval the same way, with no agent and no wallet cap: the envelope binds `sweepHash(sweep)`; assertions are checked at the workspace's admin threshold; a paused workspace can be swept; and the destination must be on the wallet's current recipient allowlist or be a treasury wallet of the same workspace (`sweep_destination_not_allowed` otherwise). The signer builds the native transfer or the ERC-20 `transfer(to, amount)` itself and signs once per approval.

There is no route for messages, typed data, raw hashes or EIP-7702 authorizations. Any path or method the contract does not name answers 404.

## Mandates

A mandate lets one agent transfer bounded amounts from one wallet to listed recipients for a while, with no passkey per payment (`docs/approval-protocol.md`, section 8, "Mandates"; `specs/approval-mandates.md`). Five routes, all in the control scope, in `mandates.ts`:

- `PUT /v1/mandates/:mandateId` with `{ mandate, authorization }` grants it. The envelope is `grant-mandate`, approved on the confirmation page at the workspace's admin threshold, within `SIGNER_MAX_ADMIN_TTL_SECONDS`, with the same idempotency, restore fence and nonce rule as every admin change. In place of the envelope and policy steps: the path id, `envelope.mandateId` and `mandate.id` are equal, the envelope's workspace, wallet and agent are the mandate's and the wallet belongs to that workspace, and `mandateHash(mandate)` is the envelope's (`envelope_mismatch`); the wallet has a policy (`policy_missing`); `checkMandateAgainstPolicy` passes with the current policy, the signer's clock and `SIGNER_MAX_MANDATE_SECONDS` (`mandate_invalid` with the reason as `detail`); the wallet has fewer live (not revoked, not past `notAfter`) mandates than `SIGNER_MAX_LIVE_MANDATES_PER_WALLET` (`mandate_invalid`, `too_many_live_mandates`); and no mandate already has this id (`conflict`). These checks run before the assertions are verified and again in the transaction that stores the mandate, its grantors (one per assertion) and the nonce. A repeat of the same grant returns the stored state, revoked or not. An unknown wallet is `not_found`.
- `POST /v1/mandates/:mandateId/sign` with `{ approvalId, intent, transaction }` signs one transfer under it. Everything runs in one SQLite transaction with no `await` inside, in this order: the mandate exists (`not_found`); the use id was revoked (`approval_revoked`), was signed as this use (same `mandateUseDigest`: the stored transaction comes back, even while paused or after the mandate ended) or names anything else (`conflict`); the workspace is not paused (`workspace_paused`); the mandate is not revoked (`mandate_revoked`) and the signer's clock is in `[notBefore, notAfter)` (`mandate_not_yet_valid`, `mandate_expired`); its grantors are at least the current admin threshold (`mandate_denied`, `mandate_grant_below_threshold`); the intent was never used under a mandate (`conflict`); the wallet's current policy allows the intent against the last 24 hours, mandated spending included (`policy_missing`, `policy_denied` with the rule); `evaluateMandate` allows it against the mandate's own count (`mandate_denied` with the rule); the fee fits (`fee_cap_exceeded`). Then the signer builds, signs and checks the transaction as for an approved intent and stores the approval row (its digest is the use's `mandateUseDigest`), the signature, the spend and the use together. Every use counts for good, including one the network never mines.
- `POST /v1/mandates/:mandateId/revoke` with `{ workspaceId }` ends it for good with reason `requested`; a mandate of another workspace is `not_found`, and revoking twice changes nothing. There is no resume. The signer also revokes mandates itself, each in the transaction of its cause and each recorded under the grant's approval id: removing an approver's passkey revokes every live mandate that passkey granted (`grantor_removed`, decision `revoke-mandate-on-grantor-removal`); every move of the restore fence revokes every live mandate (`operator`, `revoke-mandate-on-fence`); the admin CLI revokes one or a workspace's (`operator`, `revoke-mandate-by-operator`).
- `GET /v1/mandates/:mandateId` and `GET /v1/wallets/:walletId/mandates` return `MandateState`: the mandate and its hash, the grant's approval id, time and grantors, the revocation, and the usage (uses; per asset the total and what moved in the last `windowSeconds`), with a status computed when asked: `revoked`, else `not_yet_valid` or `expired` by the clock, else `exhausted` (`maxUses` reached or every asset at its `maxTotal`), else `active`. A wallet's list is ordered by `notAfter`, then id.

A use's approval id also answers `GET /v1/approvals/:approvalId` as `signed` with its transaction hash, and `POST /v1/approvals/:approvalId/revoke` before the use stops it (`approval_revoked`).

## Reprices and cancels

A transaction the signer signed may never be mined. The signer then signs further attempts of the same approval, all at the account nonce of its first signature, so at most one of them can be mined (`docs/approval-protocol.md`, section 8, "Reprices and cancels"; `specs/stuck-transaction-repricing.md`). Attempt 0 is the `signatures` row; every later one is a `signature_attempts` row. Two routes, both in the control scope, in `attempts.ts`; in both, `:approvalId` is the approval that was signed:

- `POST /v1/approvals/:approvalId/reprice` with `{ intent, envelope, attempt, maxFeePerGas, maxPriorityFeePerGas }` signs the same transaction with both fees higher, with no passkey. `envelope` is the `approve-intent` envelope people approved, without assertions: its digest must be the one the signer stored (`conflict`) and `intentHash(intent)` its `intentHash` (`intent_mismatch`). A use of a mandate sends `mandateId` in place of `envelope`: the signer must have recorded the approval id as a use of that mandate (`conflict`), with the use digest of that intent (`intent_mismatch`). A repeat of an attempt that exists with the same fees returns it; then, in order: the first signature was made after the restore fence (`envelope_fenced`), the workspace is not paused (`workspace_paused`), the mandate is not revoked (`mandate_revoked`), the signer's clock is before the first signature plus `SIGNER_REPRICE_WINDOW_SECONDS` (`reprice_window_closed`), `attempt` is the latest plus one (`conflict`) and below `SIGNER_MAX_TX_ATTEMPTS` (`attempts_exhausted`), both fees are strictly above the latest attempt's (`fee_not_raised`) with the tip at most the fee cap, and `gas × maxFeePerGas ≤ min(intent.maxFeeWei, current policy fees.maxPerTxWei)` (`fee_cap_exceeded`). The signer rebuilds the transaction from the intent with the first signature's nonce and gas, and refuses (`internal`) unless everything but the two fees equals the first signature.
- `POST /v1/approvals/:approvalId/cancel` with `{ authorization, attempt, maxFeePerGas, maxPriorityFeePerGas }` signs a transfer of nothing from the wallet to itself at the same nonce, gas 21000. The envelope is `cancel-transaction`, approved on the confirmation page at the wallet policy's threshold and lifetime; its `targetApprovalId` is the path's, and its wallet, chain and `txNonce` those of the target's first signature (`envelope_mismatch`); its `maxFeeWei` is at most the policy's `fees.maxPerTxWei` and bounds `21000 × maxFeePerGas` (`fee_cap_exceeded`). It has the idempotency, restore fence and nonce rule of every envelope, and the attempt-number and fee rules of a reprice. A paused workspace may cancel, after the window too, and a transaction signed before the fence too: a cancel moves nothing and carries its own passkeys.

Once an approval has a cancel, every later attempt is a cancel: a reprice rebuilds the self-transfer under that cancel's `maxFeeWei` (and the policy's current `fees.maxPerTxWei`, if lower), and a second cancel approval may raise it. No attempt adds or removes a spend or a mandate use: the first signature's counts stand whichever attempt is mined, also when a cancel lands. A sweep has no intent to rebuild from, so its transaction can be cancelled but not repriced.

Why a reprice of a transaction signed before the restore fence is refused: a restored database may have forgotten attempts signed after its backup, a cancel among them, and a reprice built from what it remembers could turn that cancel back into the payment. A reprice adds no authority beyond the fee, but it is a signature. Why a revoked mandate stops the reprices of its uses while expiry does not: revoking is a person's (or the operator's) word that the agent's standing authority ends, while a use made before expiry was counted when the mandate was live and a reprice is that same use.

`GET /v1/approvals/:approvalId` lists a signed approval's attempts in `attempts`, the first included; for a `cancel-transaction` approval it reports `applied` with the one attempt it produced and its hash. Decision-log actions: `reprice` under the signed approval's id, `cancel-transaction` under the cancel's approval id.

## Confirmation pages

The confirmation page lets a person read an approval as the signer holds it and approve it there, on its own origin, so the control plane cannot show one operation and collect a passkey assertion for another (`specs/trusted-display.md`). It is the only place an approval is made, for every envelope kind. Six routes, in `confirmations.ts`:

- `POST /v1/approvals/:approvalId/confirmation` (control scope) opens it with `{ envelope, subject }`, where the subject is the intent, the policy, the sweep or the mandate whose hash the envelope names, or `envelope-only`. The signer checks that the subject is exactly what the envelope names (`intent_mismatch`, `envelope_mismatch`), that the workspace and wallet exist, that the envelope has not expired, that the approval was not revoked (`approval_revoked`) or used (`confirmation_closed`), and that it could still act on it: not fenced (`envelope_fenced`); for a payment or a policy change the wallet's policy is still the one it names (`policy_missing`, `policy_changed`); for a mandate grant the wallet has a policy and the mandate fits it, the clock and `SIGNER_MAX_MANDATE_SECONDS` (`policy_missing`, `mandate_invalid` with the reason); for a cancel the wallet has a policy whose fee cap is at least the cancel's `maxFeeWei` and the target has an attempt left (`policy_missing`, `fee_cap_exceeded`, `attempts_exhausted`). A cancel is opened only for a target that is a signed approval of the workspace with the envelope's wallet, chain and nonce (`envelope_mismatch`); its view shows what that transaction would do, read back from the bytes the signer signed. The same conditions make an open confirmation `superseded`; a grant becomes `open` again if the policy is edited back to admit it. The cap on live mandates is not one of them: it only waits for a mandate to end. It stores both and answers `{ path: "/a/<approvalId>#<token>" }` with a fresh 16-byte token, keeping only its SHA-256. Opening again with the same envelope issues a new token and the old link stops working; another envelope for the same approval is `conflict`.
- `GET /v1/confirm/:approvalId` (confirm scope, token in `x-confirm-token`) returns the view: its state (`open`, `complete`, `expired`, `revoked`, `used` or `superseded`), the lines `renderConfirmation` builds from the stored envelope and subject and the signer's own records (wallet label and address, current policy, 24-hour spend in the payment's asset, admin threshold, treasury wallets, the operator's labels), the approvals collected and required, and the WebAuthn options: the envelope's digest as challenge, the passkeys of approvers who have not approved yet, user verification required. A wrong token is `not_found`.
- `POST /v1/confirm/:approvalId/assertions` (confirm scope) takes `{ response }`, one assertion. More than 64 submissions per approval are `rate_limited`. The state must be `open` (`confirmation_closed`); the passkey must be one of the workspace's approvers (`approver_unknown`); the browser must have made the assertion at `SIGNER_APPROVAL_ORIGIN`, top-level, as a `webauthn.get` (`assertion_invalid`); one per person (`conflict`). It answers `{ collected, required, returnUrl }`.
- `GET /v1/approvals/:approvalId/assertions` (control scope) lists the stored assertions of people who are still approvers with the same passkey, with the signer's own user id for each. The control plane sends them back to sign or apply, and the signer verifies them again there.
- `GET /v1/confirm/:approvalId/possession` (confirm scope, token in `x-confirm-token`) returns the possession step of an `add-approver` request: the WebAuthn options with `possessionChallenge({ approvalId, credentialId, nonce })` as challenge, the envelope's credential id as the only allowed passkey, user verification required. The nonce is 16 random bytes in table `possession_challenges`, made on the first request and kept until an answer uses it. Any other kind of request is `not_found`; a request that is not `open` or `complete` is `confirmation_closed`.
- `POST /v1/confirm/:approvalId/possession` (confirm scope) takes `{ response }`, the person being added's answer. It counts toward the same 64 submissions. The answer must come from the envelope's credential and verify against the envelope's public key, made at `SIGNER_APPROVAL_ORIGIN`, top-level, as a `webauthn.get` (`assertion_invalid`); an answer to a used or absent challenge is also `assertion_invalid`. On success the signer deletes the nonce, records `possession_proven_at` on the confirmation (the first proof stays), and answers `{ fingerprint }`, the key's fingerprint for the person to read to the approvers.

Until the proof, the view of an `add-approver` request carries the warning `possession_unproven`, `POST /v1/confirm/:approvalId/assertions` refuses an approval of it with `possession_unproven`, and `POST /v1/workspaces/:workspaceId/approvers` refuses to apply it with `possession_unproven` unless the confirmation of that exact envelope records the proof. The operator's `enroll-approver` has no such step.

A payment needs its policy's threshold, a cancel its wallet's current policy's; every other kind needs the admin threshold. Confirmations and possession proofs add no authority, so they are logged to stdout (`confirmation.opened`, `confirmation.assertion` and `confirmation.possession` with outcome and code, `confirmation.rate_limited`), not to the decision log; a refusal to apply an `add-approver` with `possession_unproven` is in the decision log like every other refusal. Nothing in a log line carries a token, an intent or an assertion.

| `unauthenticated`               | 401  | The request signature is missing, wrong, or more than 60 seconds from the signer's clock.                                                          |
| `not_found`                     | 404  | Unknown route, workspace, wallet, approver or mandate, or a mandate of another workspace.                                                          |

| `confirmation_closed`           | 409  | The approval can no longer collect assertions: revoked, used, expired, superseded or complete.                                                     |
| `possession_unproven`           | 409  | The person being added has not proven on the confirmation page that they hold the passkey an approver change adds.                                 |
| `rate_limited`                  | 429  | More than 64 assertions were submitted for one confirmation.                                                                                       |
| `workspace_paused`              | 403  | The workspace is paused; nothing signs until a passkey-approved resume.                                                                            |
| `approval_revoked`              | 403  | The approval id was revoked; it will never sign or apply.                                                                                          |
| `envelope_mismatch`             | 403  | The envelope is the wrong kind, or names another workspace, wallet, agent, chain or policy.                                                        |
| `envelope_expired`              | 403  | The envelope's `expiresAt` has passed.                                                                                                             |
| `envelope_not_yet_valid`        | 403  | The envelope is dated more than 30 seconds in the future.                                                                                          |

| `envelope_fenced`               | 403  | The envelope was issued before the restore fence (plus 30 seconds); propose it again.                                                              |
| `nonce_reused`                  | 403  | The envelope's nonce was already used by another approval.                                                                                         |
| `intent_mismatch`               | 403  | The intent is not the one that was approved (any field changed).                                                                                   |

| `policy_denied`                 | 403  | The policy refuses the intent; `detail` carries the reason (for example `over_daily_cap`).                                                         |
| `policy_invalid`                | 403  | A new policy is not the next revision of the hash chain.                                                                                           |
| `fee_cap_exceeded`              | 403  | The fee would exceed the approved ceiling, or the priority fee exceeds the max fee.                                                                |
| `insufficient_approvals`        | 403  | Fewer different approvers signed than the threshold requires.                                                                                      |
| `assertion_invalid`             | 403  | An assertion does not verify for this envelope, origin, RP ID or user verification.                                                                |
| `approver_unknown`              | 403  | An assertion comes from a passkey that is not (or no longer) an approver of the workspace.                                                         |
| `threshold_unreachable`         | 403  | The change would leave a threshold that the remaining approvers cannot meet, or would lower the admin threshold below a wallet's policy threshold. |

| `mandate_revoked`               | 403  | The mandate was revoked; nothing more is signed under it.                                                                                          |
| `mandate_expired`               | 403  | The signer's clock is at or past the mandate's `notAfter`.                                                                                         |
| `mandate_not_yet_valid`         | 403  | The signer's clock is before the mandate's `notBefore`.                                                                                            |
| `mandate_denied`                | 403  | The mandate does not cover the intent; `detail` is a `MandateDenyCode` (for example `mandate_over_window_cap`, `mandate_grant_below_threshold`).   |
| `mandate_invalid`               | 403  | The mandate cannot be granted; `detail` is a `MandateGrantRefusal` (for example `lifetime_too_long`, `too_many_live_mandates`).                    |
| `fee_not_raised`                | 403  | A reprice or cancel does not raise both fees above the latest attempt's.                                                                           |
| `attempts_exhausted`            | 403  | The approval has `SIGNER_MAX_TX_ATTEMPTS` attempts, the first signature included.                                                                  |
| `reprice_window_closed`         | 403  | `SIGNER_REPRICE_WINDOW_SECONDS` passed since the first signature: only a cancel, with passkeys, is signed now.                                     |
| `vault_error`                   | 500  | The key store failed, or a wallet was requested while the owner passphrase file is absent.                                                         |
| `internal`                      | 500  | Anything else. Nothing about it is returned; the log has the failing route.                                                                        |

## Configuration

| Variable                              | Meaning                                                                                                                             |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `SIGNER_PORT`                         | Listener port (default 8787).                                                                                                       |
| `SIGNER_DATA_DIR`                     | Holds `signer.sqlite` and `vault/`.                                                                                                 |
| `SIGNER_HMAC_SECRET_FILE`             | Base64 file, at least 32 bytes: the request-signing secret shared with the control plane.                                           |
| `SIGNER_CONFIRM_SECRET_FILE`          | Base64 file, at least 32 bytes, not the request secret: shared with the `approve` service.                                          |
| `SIGNER_KEY_FILE`                     | Base64 file, exactly 32 bytes: seals the per-wallet OWS tokens stored in SQLite.                                                    |
| `SIGNER_VAULT_PASSPHRASE_FILE`        | The OWS owner passphrase, read only when a wallet is created. Absent: existing wallets still sign.                                  |
| `WEBAUTHN_RP_ID`                      | The relying party ID passkeys were registered under.                                                                                |
| `SIGNER_APPROVAL_ORIGIN`              | The confirmation page's exact origin, the only one an approval may be made at: a host under `WEBAUTHN_RP_ID` or another port on it. |
| `SIGNER_RETURN_ORIGIN`                | The control plane's origin, where the confirmation page sends people afterwards.                                                    |
| `SIGNER_CHAINS_FILE`                  | The control plane's chains file; the signer reads each chain's id, `name` and `nativeSymbol`.                                       |
| `SIGNER_ASSETS_FILE`                  | JSON array of `{ chainId, asset, symbol, decimals }` for the tokens the page names.                                                 |
| `SIGNER_MAX_INTENT_TTL_SECONDS`       | Ceiling on an intent approval's lifetime (default 86400).                                                                           |
| `SIGNER_MAX_ADMIN_TTL_SECONDS`        | Ceiling on other envelopes' lifetime (default 86400).                                                                               |
| `SIGNER_MAX_MANDATE_SECONDS`          | Longest mandate life granted, from now or its `notBefore` if later: 3600 to 2592000 (default 604800, seven days).                   |
| `SIGNER_MAX_LIVE_MANDATES_PER_WALLET` | Live (not revoked, not past `notAfter`) mandates one wallet may hold: 1 to 64 (default 16).                                         |
| `SIGNER_MAX_TX_ATTEMPTS`              | Attempts per approval, the first signature included: 2 to 64 (default 16).                                                          |
| `SIGNER_REPRICE_WINDOW_SECONDS`       | How long after the first signature a reprice is signed with no person: 0 to 604800 (default 86400; 0 refuses every reprice).        |

`WEBAUTHN_ORIGINS` is no longer read; remove it from an older environment. The signer refuses to start when a secret is missing or malformed, when the confirm secret equals the request secret, when `SIGNER_APPROVAL_ORIGIN` is not under the RP ID or equals `SIGNER_RETURN_ORIGIN` (the control plane's origin), or when a label file has a name or symbol that could pass for something else (symbols `^[A-Za-z0-9.]{1,11}$`, chain names printable ASCII up to 40 characters, decimals 0 to 36). It runs with umask 077, and on SIGTERM finishes requests in flight before closing the database.

```sh
node src/main.ts
```

## Admin CLI

Runs on the signer host, with the same environment, against the same SQLite file:

```sh
node src/admin.ts enroll-approver --workspace ws_… --user usr_… \
  --credential-id <base64url> --public-key <base64url COSE key>
node src/admin.ts verify-log --workspace ws_…
node src/admin.ts fence
node src/admin.ts list-mandates --workspace ws_…
node src/admin.ts revoke-mandate --mandate mnd_…
node src/admin.ts revoke-mandate --all --workspace ws_…
```

Each command prints one JSON line. `enroll-approver` adds exactly the passkey typed on the command line as an approver of the workspace, in one transaction with an `enroll-approver-by-operator` entry in the decision log; it refuses an unknown workspace (`not_found`) or a credential already enrolled (`conflict`). It is how a workspace whose people lost every passkey regains control; its wallets are untouched. There is no HTTP route for this: anything relayed over HTTP passes through the control plane, which could swap in its own key. **Host access is the root of trust:** whoever can run this command on the signer host can add an approver, so treat shell access to that host as signing authority.

`fence` sets the restore fence to the host's clock (it never moves it back), records `fence-set-by-operator` in every workspace's decision log, and revokes every live mandate (see "Restoring"). It prints `{"ok":true,"action":"fence-set-by-operator","fenceAt":…}`. Run it after every restore, before the signer serves.

`list-mandates` prints the workspace's mandates as identifiers, status, times and use counts, never their purpose or recipients. `revoke-mandate --mandate` ends one mandate, and `revoke-mandate --all --workspace` every live mandate of a workspace, with reason `operator` and one `revoke-mandate-by-operator` entry each; both print `{"ok":true,"action":"revoke-mandate-by-operator","revoked":[…]}` with the ids they revoked (none for a mandate already revoked). An unknown workspace or mandate is `not_found`.

`verify-log` recomputes the workspace's decision-log hash chain and compares its end with the head stored on the workspace row, which every append updates in the same transaction. It detects damaged, edited or deleted rows, including the newest ones. The chain is not keyed, so someone who can write the SQLite file can rewrite every row and the head consistently; it does not detect that.

## Decision log

Recorded, per workspace: every allowed change (workspace creation, wallets, policies, approvers, thresholds, pause, resume, signatures, sweeps, reprices, cancels, revocations, operator enrollment, restore fences, mandate grants, uses and revocations) and every refusal of a request that passed the request signature and the body's schema and names a workspace the signer knows. Not recorded: requests with a missing or bad request signature, malformed bodies or paths, requests for workspaces, wallets or approvals the signer does not know (`not_found`), and refusals before a workspace is resolved. Those appear only as one JSON line on the signer's stdout with the route and code.

## Back up

Back up `SIGNER_DATA_DIR` (the SQLite file and the vault together), `SIGNER_KEY_FILE` and the owner passphrase.

- The vault alone holds every wallet's mnemonic, encrypted under the owner passphrase.
- The SQLite file holds the sealed OWS tokens, the policies, the approvers and the used nonces. Restoring an older copy forgets nonces that were used since.
- Without `SIGNER_KEY_FILE` the stored tokens cannot be opened; the passphrase can still recover the wallets from the vault.
- Read access to the vault plus a token is the wallet's key. Keep the volume readable by the signer's user only.

## Restoring

Every restore is fenced, because nothing in a backup says whether a payment happened after it. Run `node src/admin.ts fence` before the signer serves. From then on the signer refuses every envelope issued before the fence plus 30 seconds (`envelope_fenced`), so an approval used after the backup cannot be signed again; approvals waiting at the restore must be proposed again. An approval this database already signed still returns its stored transaction, and its attempts already stored are still answered, but it gets no new reprice (`envelope_fenced`): it can only be cancelled. Every move of the fence also revokes every live mandate with reason `operator`: the restored database forgot the uses counted after the backup, so its counts would let more leave the wallet than people approved. Grant them again.

The signer also records which file its database is (inode and creation time) and fences by itself when it opens another one: a copy, an extracted archive, a move to another host. It logs `restore fence set` with `reason: new_database_file` and records `fence-set-on-new-database-file`. It cannot tell a restore that rolls the same file back in place (a disk snapshot), so the operator's step stays. The first start on a v0.1 file fences once, because no file was recorded.
