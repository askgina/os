# Research: a self-hosted Busy fork on askgina/os

## Question

Busy (https://github.com/MatiSolina/busy, Apache-2.0, https://busybot.dev/) needs Vercel projects, Sandbox and Drive, so v0.1 dropped it. The owner still wants it. What exactly ties Busy to Vercel, what would a fork replace each tie with, how would its bots use the MCP gateway and the encrypting World, and how large is the fork to keep in step with upstream?

## Answer

- Busy has 13 ties to Vercel (table in F2). Eight groups of them matter for a self-hosted install: per-bot Vercel projects and deployments (with their environment variables and domains), Sandbox, Drive, Blob, Queues, Schedules, the AI Gateway, and Vercel OIDC as the bot identity. The rest are observability, an optional Vercel sign-in and the container registry. Two features, code tasks and firesides, are built on Vercel-only libraries.
- Each tie has a self-hosted replacement: one container per bot started by a runner service, one gVisor container per bot computer with a per-bot volume in place of a Drive, S3-compatible storage in place of Blob, a Postgres-backed scheduler and an in-process consumer in place of Schedules and Queues, an OpenAI-compatible endpoint in place of the AI Gateway, and a Hub-issued per-bot token in place of OIDC.
- Busy already has four injection seams (bot deploy, routine schedules, model decision, embeddings endpoint) and eve 0.91.0 has a World seam and a sandbox-provider seam. The eve report's "no interface" is too strong.
- Bots reach askgina/os only through the MCP gateway with their own agent token, like the eve example. Busy's approval card must be switched off for the seven tools: its answer is a cookie-authenticated HTTP POST to the Busy Hub, which the signer cannot verify and must never accept. The passkey approval in the askgina/os inbox stays the only approval.
- Bots and the Hub can run on `@askgina/os-world/target`. The Busy Hub also keeps chat messages, eve events and memories in plaintext in its own Postgres tables, which the World does not cover.
- The smallest honest fork is about 4,000 to 5,000 new or changed lines touching about 40 upstream files `[INFERENCE]`, with code tasks, firesides, bot-to-bot consultations and the Desktop app switched off. Upstream is five days old and moves in bursts of large "Sync" commits, and its eve dependency ships more than one release a day, so the fork needs an automated upstream-rebase gate.

## Findings

### F1. Upstream shape and size

- Busy is a pnpm monorepo: `apps/hub` (Next.js 16.4.3 control plane), `apps/desktop` (Electron), `templates/bot` (the eve agent deployed once per bot), `images/bot-base` (the bot computer image), `skills/busy-setup` (`README.md:18-25`, `apps/hub/package.json`).
- Size, counted on `busy@3dd91e1`: 1,132 files. `apps/hub` has 781 files, 82,657 lines of non-test TypeScript and 58,430 lines of test TypeScript. `templates/bot` has 207 files and 20,992 lines of TS/JS including tests. `images/bot-base` has 27 files.
- The Hub owns identity, policy, persistence and orchestration; each bot is "an independently deployable Eve application with its own Vercel project, durable session and isolated computer" (`docs/architecture.md:8-11`).
- The bot template pins `eve` 0.91.0 (`templates/bot/package.json:26`), published 2026-10-30. The eve example in this repository uses `eve` 1.0.0-rc.17 (`os@61dd59c:examples/eve-agent/package.json`). npm lists 18 eve releases after 0.91.0 up to 1.0.0-rc.18 (2026-11-14T17:09Z) and 60 releases since 2026-10-01 (`npm view eve time`).

Two features are built on Vercel-only libraries and have no small replacement:

- **Code tasks** (8,835 non-test lines under `lib/code-tasks` and its routes) run `durable-harness` 0.0.1 and `libfx` 0.0.16 (`apps/hub/package.json:57,61`; `lib/code-tasks/runtime.ts:1-12`). npm metadata for `durable-harness` 0.0.1 lists `@vercel/oidc` 3.2.0 and `@workflow/world-vercel` as dependencies and `@vercel/sandbox` and `@vercel/agent-runs` as peers; its repository is `vercel-labs/durable-harness`.
- **Firesides** (a second agent giving the bot a "second opinion", `docs/second-opinion.md`) reach the Gateway through `app/api/bot/firesides/gateway/language-model/route.ts` and their own Drives (`templates/bot/agent/sandbox.ts:59-66`).

### F3. Seams that already exist

The eve report says the Busy couplings are imported directly "with no interface" (`os@61dd59c:specs/research/eve-without-vercel-services.md:18`). For the bot template that is true. For the Hub it is too strong:

- `DeployDeps` is an injected interface for every deploy side effect (`apps/hub/lib/bots/deploy.ts:13-39`), built in one place (`lib/bots/service.ts:122-143`).
- `SchedulesClient` is a default parameter (`lib/routines/schedule.ts:52,93`; `lib/routines/outbox.ts:130`).
- The Decision API is an injected `DecisionRunner` with a fallback to the first catalog model (`lib/bots/creation.ts:28-31,75-81`).
- The embeddings endpoint is configurable (`lib/history-search.ts:294-303`).
- eve 0.91.0 resolves any World package specifier other than `local` and `vercel` (`eve@0.91.0:dist/src/internal/workflow/world-target.js`) and ships `./sandbox/provider`, `./sandbox/docker` and `./sandbox/just-bash` exports (`eve@0.91.0:package.json`, `exports`).

### F4. The Busy Hub keeps conversation content in plaintext

The encrypting World covers workflow payloads only. Busy's Hub writes conversation content to its own tables, readably:

- `messages.text` (`apps/hub/lib/db/schema.ts:790-819`), `events.data` (eve stream records, `:726-733`), `memories.content` (`:611-615`), `history_embeddings.text` (`:972-991`), routine prompts (`:474,527`), bot instructions (`:91`).
- History search runs Postgres full-text search over that text (`lib/history-search.ts:167-183`, `to_tsvector('simple', d.text)`), so sealing those columns would break search.
- Busy does seal MCP credentials and provider grants (`schema.ts:305,348,368,1432,1455`).

So "a database copy without the keyring holds nothing readable" would be true for the bots' World databases and false for the Busy Hub database. `[INFERENCE]` A fork must state that, or seal those columns and give up full-text search.

### F5. eve 0.91.0 on the encrypting World

- The World seam works the same way as in rc.17: `experimental.workflow.world` takes a package specifier (F3). Busy sets only `workflow: { retention: "default" }` today (`templates/bot/agent/agent.ts:26-29`).
- eve 0.91.0 compiles in `@workflow/core` 5.2.3, `@workflow/world` 5.0.5 and `@workflow/world-local` 5.1.2 (development dependencies at `eve@0.91.0:package.json:644-649`, imported from `dist` as `#compiled/@workflow/...`). `@askgina/os-world` is built on `@workflow/world` 5.2.0 and `@workflow/world-postgres` 5.2.0 (`os@61dd59c:packages/world/package.json`). Compatibility between the two is not proven `[INFERENCE]`; it needs the same ciphertext test the eve example has.
- A string search of eve 0.91.0's `dist` finds 25 `$eve.` keys: `$eve.type`, `$eve.version`, `$eve.session`, `$eve.root`, `$eve.parent`, `$eve.parent_call`, `$eve.parent_turn`, `$eve.subagent`, `$eve.trigger`, `$eve.prewarm`, `$eve.schedule`, `$eve.title`, `$eve.trace_id`, `$eve.channel_request_id`, `$eve.is_trace_content_visible`, `$eve.is_otel_trace_enabled`, `$eve.invocation_token`, `$eve.invocation_owner`, `$eve.model`, `$eve.input_tokens`, `$eve.output_tokens`, `$eve.cache_read_tokens`, `$eve.cache_write_tokens`, `$eve.cost_usd`, `$eve.tool_count`. Some of them may be telemetry span attributes rather than run attributes `[INFERENCE]`. The World withholds every run attribute value not listed in `WORLD_READABLE_ATTRIBUTE_KEYS` (`os@61dd59c:packages/world/README.md:45-60`), so the readable list must be derived again for every eve version a fork takes. The eve example's list for rc.17 is the starting point (`os@61dd59c:examples/eve-agent/compose.yaml:77`).
- `$eve.invocation_token` is a continuation token that eve reads back from the run (`eve@0.91.0:dist/src/internal/invocation/metadata.js`, `buildInvocationAttributes`; `workflow-execution.js`, `token: t.attributes[INVOCATION_TOKEN_ATTRIBUTE]`). Withheld, eve's invocation API cannot work; listed, a bearer token is stored readably. The same attribute exists in rc.17 (`dist/src/internal/invocation/attributes.js`), and the eve example's list leaves it out (`os@61dd59c:examples/eve-agent/compose.yaml:77`). Busy's Hub uses eve's session API, not invocations (`apps/hub/lib/eve/client.ts`), so a fork can leave the key withheld `[INFERENCE]`.
- Busy's channel sets no session title (`templates/bot/agent/channels/eve.ts:12-43`), so eve's default title, the first user message, goes into `$eve.title`. eve 0.91.0 accepts a `title` from `onMessage` (`eve@0.91.0:dist/src/eve-channel/types.d.ts:83-84`), so the fork can fix the title as the eve example does (`os@61dd59c:examples/eve-agent/agent/channels/eve.ts`, last lines).

### F6. Busy's approval cards applied to the seven gateway tools

Busy's MCP connections carry an eve approval policy that classifies each tool by its MCP annotations or, without them, by the first word of its name (`templates/bot/agent/lib/approval.ts:111-126`). Reads pass; everything else asks the person in chat (`:128-146`). The card's text is built from the tool name and the first three of a fixed list of input keys, at most 160 characters (`:246-315`). The gateway's tools carry no annotations (`os@61dd59c:apps/server/src/mcp/gateway.ts:161-364`). Applied to them, `[INFERENCE]` from the code:

| Gateway tool            | Busy classification                                    | Busy card text (shape)                                                                                                           |
| ----------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| `whoami`                | read (`whoami` is a read verb, `approval.ts:29`)       | none                                                                                                                             |
| `get_balances`          | read (`get`)                                           | none                                                                                                                             |
| `get_intent`            | read (`get`)                                           | none                                                                                                                             |
| `list_intents`          | read (`list`)                                          | none                                                                                                                             |
| `propose_transfer`      | write (`propose` is not a read verb)                   | "I'm about to move money in … (propose transfer). to: 0x…, amount: 0.05 … OK?" (`transfer` is a money verb, `approval.ts:49-62`) |
| `propose_contract_call` | write                                                  | "I'm about to use "propose contract call" in … OK?"                                                                              |
| `cancel_intent`         | write (`cancel` is a delete verb, `approval.ts:34-47`) | "I'm about to delete or cancel something …"                                                                                      |

So an unmodified Busy would show a card that says money is about to move, when nothing moves: the proposal only records a request that a person must approve with a passkey. Busy's card must not become the authorization, for these reasons:

1. **What it proves.** The answer is `POST /api/bots/<slug>/answer` with an `optionId` (`apps/hub/app/api/bots/[slug]/answer/route.ts:11-30`), authenticated by the Busy Hub's session cookie and password login. It is not a passkey assertion over an intent digest, so the signer cannot check it (`os@61dd59c:docs/approval-protocol.md`, sections 5 and 6).
2. **Who can forge it.** The Hub records the answer and forwards it to eve; a compromised Hub or bot can answer its own card. eve's documentation says the same: "Approval is consent only" (`eve@0.91.0:docs/tools/human-in-the-loop.md:46`) and "A remembered approval is consent, not authorization" (`:152`).
3. **What it shows.** The card text is a heuristic summary, not the canonical intent the signer builds the transaction from.
4. **What it would invite.** Two prompts for one payment teach people to approve the second without reading it.

The askgina/os approval link must open as a top-level page, not inside Busy's MCP App iframe: the askgina/os pages send `frame-ancestors 'none'` (`os@61dd59c:packages/api/src/csp.ts:22`), and the passkey is bound to the askgina/os origin.

### F7. Where a Busy bot can sit on the askgina/os networks

- The `agents` network is `internal: true` and its only service is the agent gateway, which forwards `/mcp` alone on port 80 (`os@61dd59c:compose.yaml:132-144,183-184`; `deploy/Caddyfile.agents:9-18`). A Busy bot also needs egress (model endpoint, Hub, web fetches), so it must join `agents` and a second, egress network. It must never join `control`, `signing` or `chain`.
- Busy's Hub refuses MCP endpoints on loopback, private, `.local` and `.internal` hosts (`apps/hub/lib/mcp/network.ts:60-64,197-207,232-240`) and supports only `oauth` or `none` auth for MCP connections (`templates/bot/agent/connections/marketplace.ts:20`). So the gateway cannot be added as a Busy marketplace connection without changing that code. A connection defined in the bot itself, with the agent token as a bearer header, avoids both (eve 0.91.0's `defineMcpClientConnection` takes `auth`, `headers`, `approval` and `tools`: `eve@0.91.0:dist/src/public/definitions/connections/mcp.d.ts:14-112`). This is what the eve example does with its own MCP client (`os@61dd59c:examples/eve-agent/lib/gateway.ts`).
- The bot computer runs browser and shell work driven by untrusted web content. It must not join `agents`, so code running there cannot reach the gateway. The agent token lives in the bot process, not in the computer.
- Whatever starts containers holds a Docker daemon socket, which is root on that host `[INFERENCE]`, standard Docker behavior. On the same host as the signer, that makes the runner a "signer host" position, the v0.1 limit "One machine running everything gives no protection against that machine" (`os@61dd59c:docs/threat-model.md:216-218`).

### F8. Licence, attribution and trademark duties

## Recommendation

**Recommendation:** build option B, laid out so that its seams can later be offered upstream (option D) if the owner chooses to.

- Keep the fork in a separate repository that carries the history of `MatiSolina/busy`. It keeps upstream history for rebasing, keeps pnpm, and keeps the Apache-2.0 boundary out of the MIT askgina/os tree.
- Put the platform replacements behind interfaces in new files: the existing `DeployDeps` and `SchedulesClient`, plus new `ObjectStore`, `BotIdentity`, a computer broker client and an OpenAI-compatible model connection. Edit upstream files only at the selection points.
- Run the runner (Docker socket) on a host or VM other than the signer's in production.
- Give each bot its own askgina/os agent and token, a bot-side MCP connection with eve approval `never()`, and a skill that sends the person to the `approvalUrl`. Never add a Busy-side route that tells askgina/os something was approved.
- Run every bot and the Hub on `@askgina/os-world/target` with a per-bot database and keyring and a fixed session title. State plainly that the Busy Hub's own tables are plaintext until a later milestone seals them.
- Switch off code tasks, firesides, consultations and Desktop, and say so in the fork's README.
- Gate every upstream rebase in CI, including a check that the eve attribute list still matches the eve version upstream pins.
