# Beyond one machine: key providers, server replicas, HA Postgres, Kubernetes

## Question

> v0.1 is one machine with a file keyring. What do a KMS or OpenBao key provider, HA Postgres, several server replicas and Kubernetes each require of the keyring, the World, the signer and the workflow queue, and which of them can be proven in CI?

## Answer

- **Only one of the four directions improves security: putting the signer on its own host with separate administration.** The threat model says so already: "the network separation between server and signer protects only when they run on different hosts with separate administration" (`docs/threat-model.md:216-218`). A key provider, replicas, HA Postgres and Kubernetes improve availability and operations. Kubernetes can weaken security if the signer runs in the same cluster, because cluster administration then equals the signer host.
- **The signer cannot be replicated as it is.** Its correctness depends on one serialized writer: used envelope nonces, the 24-hour spend ledger and "one approval, one signature" are checked and recorded in one SQLite transaction (`apps/signer/src/signer.ts:753-826`, `apps/signer/src/db.ts:113-128`). Active-active breaks that. A standby made from an asynchronous copy, or any restore from a backup older than the latest signature, can sign an already-used approval again within its expiry. A "restore fence" (refuse every envelope issued before the restore) closes that hole and is needed before any signer failover story.
- **A key provider (OpenBao Transit first) fits the existing `KeyProvider` interface with two changes:** an async `ready()` for authentication and key-version discovery, and a KEK id that carries the Transit key version so the existing rewrap path works. Transit supports AEAD associated data on encrypt and decrypt but not on its `rewrap` endpoint, so rewrap stays "unwrap, then wrap". Outages already fail closed; recovery after an outage is slow because the queue's backoff grows to about 6 hours per attempt.
- **Server replicas mostly work already**, because the queue (Graphile Worker, `SKIP LOCKED`), sessions, WebAuthn ceremonies, nonce reservations, audit appends and migrations are coordinated in Postgres. Five things do not: per-process rate limits, the boot-time setup token, the per-process key cache (shred delay), keyring rotation with a file keyring, and mixed workflow-bundle versions during a rolling upgrade (runs are not pinned to a bundle).
- **HA Postgres needs synchronous replication to keep the audit chain whole.** With asynchronous failover a lost commit removes audit entries and their head together, so the chain still verifies and the loss is invisible. Funds stay safe: the signer is idempotent per approval and keeps its own records. A lost shred commit resurrects a destroyed key.
- **Kubernetes needs NetworkPolicies that an enforcing CNI implements, and they cannot reproduce two Compose properties**: they cannot hide service names from DNS, and they cannot block `localhost` inside a pod, where the unauthenticated Workflow delivery listener lives.
- **CI can prove**: OpenBao Transit against a real OpenBao 2.7.2 container (including outage and rotation); two server replicas with a kill in the middle of a payment; Kubernetes manifests, NetworkPolicy isolation and replica crash on kind (kindnet enforces NetworkPolicy since kind v0.24.0); CloudNativePG failover with synchronous replication on kind; a signer split over mutual TLS between two Compose projects. **CI cannot prove** separate administration of two hosts, cloud KMS behaviour (IAM, quotas, latency), real network partitions, or etcd encryption.

### 2. The key provider interface and `LocalKeyring` today

- `KeyProvider` has four members: `activeKekId()`, `hasKek(kekId)`, `wrap(kekId, dataKey, aad)` and `unwrap(kekId, wrapped, aad)`; the first two are synchronous (`packages/keys/src/keyring.ts:8-15`). The comment says "A KMS-backed provider implements the same shape" (`keyring.ts:6`).
- `LocalKeyring` is AES-256-GCM with a random 12-byte IV and a 16-byte tag; a wrapped key is exactly 60 bytes and `unwrap` rejects any other length (`keyring.ts:43-44,99-119`).
- The associated data binds a wrapped key to `["askgina.os/data-key/v1", scope, keyId, tenantId, kekId]` (`packages/keys/src/data-key-store.ts:43-48`). The KEK id is inside the AAD, so a provider whose KEK id changes on rotation must rewrap by unwrapping and wrapping again, not by an opaque re-encryption that keeps the old AAD.
- `getOrCreate` checks the process cache, reads the row, creates and wraps a key on first use (`INSERT ... ON CONFLICT DO NOTHING`, then reads back so concurrent creators converge), unwraps, checks the tenant, and caches for `cacheTtlMs` (default 60 000 ms) (`data-key-store.ts:105,123-170`). There is no single-flight: concurrent cache misses in one process unwrap in parallel `[INFERENCE from the code: no in-flight map]`.
- `rewrap` walks rows whose `kek_id` differs from `activeKekId()`, unwraps under the old KEK, wraps under the active one, and updates only if the row still holds the bytes it read, so a concurrent shred is not undone (`data-key-store.ts:202-256`).
- `shred` writes a tombstone and evicts only this process's cache. The comment states that other processes keep serving the key until their TTL runs out (`data-key-store.ts:258-275`; `docs/threat-model.md:192-193`).
- The World never answers "no key": every failure throws, because upstream reads `undefined` as "store plaintext" (`packages/world/src/index.ts:39-66`; `data-key-store.ts:86-90`).
- `hasKek` has no caller except its own unit test (`packages/keys/test/keyring.test.ts:64-71`); the keys CLI uses only `activeKekId()` (`packages/keys/src/cli.ts:91`) `[source-read: grep of the repository outside node_modules]`.

### 3. What an OpenBao Transit provider must implement

Facts from the OpenBao 2.7.x Transit API ([openbao.org/api-docs/secret/transit](https://openbao.org/api-docs/secret/transit/)); the current release is v2.7.2, published 2026-10-26 ([GitHub releases API](https://api.github.com/repos/openbao/openbao/releases/latest)):

- `POST /transit/encrypt/:name` and `POST /transit/decrypt/:name` accept `associated_data` (base64) for the AEAD key types `aes256-gcm96` (the default), `aes128-gcm96`, `chacha20-poly1305` and `xchacha20-poly1305`. Encrypt accepts `key_version`. Ciphertext carries its version: `vault:v1:...`.
- `POST /transit/rewrap/:name` lists no `associated_data` parameter. So data keys wrapped with AAD cannot be rewrapped by that endpoint; the existing unwrap-then-wrap path in `DataKeyStore.rewrap` is the one to use.
- `GET /transit/keys/:name` returns every version with its creation time, plus `min_decryption_version` and `min_encryption_version`. `POST /transit/keys/:name/rotate` adds a version; raising `min_decryption_version` makes older ciphertext undecryptable.
- Every Transit call needs a token. Auth methods that fit: AppRole (`POST /v1/auth/approle/login` with `role_id` and `secret_id`, [docs](https://openbao.org/docs/auth/approle/)) for a Compose host, and Kubernetes auth (`POST /v1/auth/kubernetes/login` with a service-account JWT, [docs](https://openbao.org/docs/auth/kubernetes/)) for a pod. Tokens have a TTL and must be renewed or re-obtained.
- An OpenBao server "starts in a sealed state" and, sealed, almost nothing works, including authentication; a restart reseals unless auto-unseal is configured ([seal concepts](https://openbao.org/docs/concepts/seal/)). A sealed OpenBao is an outage of the key provider.
- Images: `quay.io/openbao/openbao`, `ghcr.io/openbao/openbao` and `docker.io/openbao/openbao`, tag `2.7.2` ([install docs](https://openbao.org/docs/install/)). Dev mode is in-memory and starts initialized and unsealed ([dev server](https://openbao.org/docs/concepts/dev-server/)), which suits a CI service container.

What the provider therefore has to do:

1. **KEK id with a version.** If the KEK id were only the key name, a Transit rotation would leave `kek_id` unchanged and `rewrap` (which selects `kek_id <> active`) would never move a row (`data-key-store.ts:222-225`). A KEK id of the form `bao:<mount>/<key>@<version>` makes rotation visible to the existing code, and `wrap` passes `key_version` so the stored version matches the AAD. `[INFERENCE: design]`
2. **Async start.** `activeKekId()` is synchronous, but finding the latest Transit version and logging in are network calls. The interface needs an async `ready()` (called by `DataKeyStore.ensureMigrated`) and a periodic refresh. `[INFERENCE: design]`
3. **Two error classes, both thrown.** "Unavailable" (network error, timeout, 5xx, 503 sealed, 429) and "refused" (403 permission, unknown key, AEAD failure). Neither may ever resolve to a value. `[INFERENCE: design; required by data-key-store.ts:86-90]`
4. **A bounded deadline.** Today `wrap` and `unwrap` are local and cannot hang. A remote call needs a timeout (the World's delivery has no deadline of its own: `DEFAULT_DELIVERY_HEADERS_TIMEOUT_MS = 0` in `node_modules/.bun/@workflow+world-postgres@5.2.0+8040c394139373db/node_modules/@workflow/world-postgres/dist/queue.js:83-84`), or a stalled provider holds a worker slot indefinitely. `[INFERENCE]`
5. **Least-privilege token.** `update` on `transit/encrypt/<key>` and `transit/decrypt/<key>`, `read` on `transit/keys/<key>`; no `rotate`, `config` or `delete`. Rotation is an operator action. `[INFERENCE: design]`
6. **Migration from the file keyring.** Rows wrapped by `LocalKeyring` (bare ids such as `k1`) must stay readable until `rewrap` moves them. A composite provider that routes `unwrap` by KEK id prefix and wraps only with Transit does that with the existing CLI (`packages/keys/src/cli.ts`). `[INFERENCE: design]`

**Latency.** Each cache miss becomes one HTTPS round trip. The v0.1 research counted 16 key requests for one 3-step run across two processes, served by 3 database reads, 1 insert and 2 unwraps with the 60 s cache ([`specs/research/encrypting-postgres-world.md`](./encrypting-postgres-world.md), finding 9). So the cache keeps provider calls at roughly two per run segment per process. No latency was measured here. With N replicas, the cold-miss count scales with N `[INFERENCE]`.

**Outage behaviour.** A provider failure throws in `getEncryptionKeyForRun`, so the delivery fails and Graphile Worker retries it. The retry backoff is `exp(min(attempts, 10))` seconds, "so each extra attempt waits ~6h", and core records `MAX_DELIVERIES_EXCEEDED` on delivery 49, which fails the run (`queue.js:105-118`). Consequences:

- No plaintext is ever written (`packages/world/src/index.ts:45-46`).
- A run that failed a handful of deliveries during an outage may wait hours after the provider recovers, because its next attempt is already scheduled far out `[INFERENCE from the formula]`. Whether restarting a server shortens that wait is unclear: start re-enqueues active runs (`dist/index.js:98-106`), but for a keyed duplicate publish "keeping the first job's `run_at` keeps that backoff" (`queue.js:701-704`) `[INFERENCE; needs a test]`.
- The same failure hits every API route that opens sealed content (`apps/server/src/db/sealed.ts`, through `DataKeyStore.getOrCreate`), so approval cards cannot be shown and people cannot approve during the outage `[INFERENCE from the call path]`.

### 4. Cloud KMS providers

- **AWS KMS.** The symmetric cryptographic request quota is shared per account and Region: 10 000, 20 000 or 100 000 requests per second depending on the Region ([request quotas](https://docs.aws.amazon.com/kms/latest/developerguide/requests-per-second.html)). AAD is the `EncryptionContext`, which "is not secret and not encrypted. It appears in plaintext in AWS CloudTrail Logs" ([encryption context](https://docs.aws.amazon.com/kms/latest/developerguide/encrypt_context.html)). Our AAD carries run and workspace ids and the tenant id, which are readable in Postgres already, so logging them is acceptable `[INFERENCE]`. Automatic rotation keeps the key ARN, so no rewrap is needed for rotation `[INFERENCE from AWS rotation model; not read here]`.
- **Google Cloud KMS.** `additionalAuthenticatedData` "must be no larger than 64 KiB", "is not stored as part of the ciphertext" and "is not logged by Cloud Audit Logs" ([AAD](https://docs.cloud.google.com/kms/docs/additional-authenticated-data)).
- Both need an SDK or signed HTTP, cloud credentials (IAM role, workload identity), and cannot be exercised in CI without a cloud account. An emulator would prove the adapter's shape, not IAM, quotas or latency `[INFERENCE]`.
- The reference conversation says the self-hosted World should be backed by "a KMS-controlled key hierarchy" and that KMS or OpenBao "can be an optional backend, not a mandatory service" (`docs/references/chatgpt-combine-encryption-approval-ux.md:104,948`). OpenBao Transit is the self-hostable form of that.

### 5. The signer as a single writer

- **State.** One SQLite file in WAL mode with `synchronous = FULL` and `busy_timeout = 5000` (`apps/signer/src/db.ts:103-111`); tables for workspaces with the decision-log head, approvers, wallets with sealed OWS credentials, policies, `used_nonces`, `approvals`, `signatures` and `spends` (`db.ts:9-101`). The OWS vault is a directory beside it (`apps/signer/src/config.ts:86-87`).
- **Serialization.** The signing decision is one synchronous `BEGIN IMMEDIATE` transaction with the vault call inside it: re-check replay, re-check pause and policy hash, check approvers, consume the envelope nonce, evaluate the intent against the last 24 hours of spends, sign, verify the signature, record approval, signature and spend (`apps/signer/src/signer.ts:753-826`; `db.ts:113-128`; `apps/signer/src/vault.ts:17-19`).
- **Correction to the ticket's wording.** Per-wallet account-nonce reservations are not signer state. The signer "does not track account nonces; the control plane reserves one per approval" (`specs/agent-workspaces-v0.1.md:153-155`). The reservation is in Postgres (`os.nonce_reservations`) under `pg_advisory_xact_lock(hashtextextended('nonce:<wallet>:<chain>', 0))` (`apps/server/src/execution/intents.ts:648-697`). Because the lock is in Postgres, it already serializes across server replicas.
- **Moving the signer to its own host requires**: a transport that keeps intents and assertions confidential and refuses unknown peers (mutual TLS; `@hono/node-server` 2.1.8 accepts `createServer` and `serverOptions` for HTTPS, `node_modules/.bun/@hono+node-server@2.1.8+5bb796a9b5bfc6ca/node_modules/@hono/node-server/dist/index.d.mts:48-61`; the signer client already accepts an injected `fetch`, `packages/protocol/src/signer/client.ts:37-42,87-88`); clocks within 60 s, because request signatures outside that window are refused (`packages/protocol/src/signer/request-signature.ts:5`, `docs/approval-protocol.md:321-322`); an `init` that writes one trust domain at a time; the operator command shown for the signer host; a host firewall with no outbound route; local block storage, because SQLite locking over network file systems is unreliable ([sqlite.org/useovernet.html](https://www.sqlite.org/useovernet.html)); and separate backups.
- **Can it be replicated?**
  - Active-active: no. Two writers would each consume nonces and count spends against a ledger the other does not see. "One approval, one signature" and daily caps would both fail `[INFERENCE from signer.ts:753-826]`.
  - Consensus-replicated storage (Raft) could keep one serialized ledger, but every replica then holds every wallet's key and sealing key, so each replica is "the signer host" (`docs/threat-model.md:139-143`). Availability improves and the number of hosts that can take all funds grows `[INFERENCE]`.
  - Warm or cold standby from an asynchronous copy (WAL shipping, Litestream-style replication, a nightly backup) loses the last writes. That is finding 6.

### 6. A restored or failed-over signer can sign a used approval again

- After a restore, the signer forgets every nonce, approval, signature and spend recorded after the backup. Step 2 (replay check) and step 8 (nonce check) of the signing rule both read those tables (`docs/approval-protocol.md:248-268`; `signer.ts:716,756-764`).
- An authorization that was used after the backup is still within its lifetime for up to `SIGNER_MAX_INTENT_TTL_SECONDS` (default 86 400, `apps/signer/src/config.ts:17`). Presented again, it passes every check. The account nonce is the caller's choice and may repeat (`signer.ts:765-768`), so a compromised control plane can choose a fresh nonce and get a second, valid transaction. Spends recorded after the backup are also gone, so the daily cap does not stop it `[INFERENCE from the code path]`.
- Even an honest control plane restored from the same older moment shows an approval that was paid after the backup as "waiting" again, and `deploy/README.md:82-83` says such approvals "can still be approved after the restore". A person who approves it again pays twice `[INFERENCE]`. `deploy/README.md:67-68` warns against restoring `signer-data` alone, but not against restoring an older whole-stack backup.
- **Fence.** Envelopes carry `issuedAt`, and the verifier already refuses an `issuedAt` more than `CLOCK_SKEW_SECONDS = 30` ahead of its clock and an envelope whose lifetime exceeds the ceiling (`packages/protocol/src/webauthn/verify-authorization.ts:44,62-69`). Every envelope used on the lost timeline was verified before the restore, so its `issuedAt` is earlier than the restore time plus 30 s. A signer that refuses every envelope with `issuedAt` before `fence + 30 s` cannot be made to repeat one. The cost: approvals that were waiting at restore time must be proposed again. `[INFERENCE: design]`

### 7. Several server replicas

**7.1 Queue.** The World's queue is Graphile Worker 0.16.6, which finds jobs with `SKIP LOCKED` and uses `LISTEN/NOTIFY` only to wake idle workers ([worker.graphile.org/docs](https://worker.graphile.org/docs); `queue.js:1154-1159`). Several processes on one database is its normal mode. Requirements:

- `jobLockStaleSeconds` must be "the same value on every process that shares the database" (`node_modules/.bun/@workflow+world-postgres@5.2.0+8040c394139373db/node_modules/@workflow/world-postgres/dist/config.d.ts:31-48`). The server hard-codes 30 (`apps/server/src/execution/workflow-runtime.ts:123-128`), so replicas of one version agree. A replica stalled for 30 s (blocked event loop, pool starvation) has its job taken over and the step runs twice, which the steps are built for (same comment).
- Each World's `start()` re-enqueues active runs; duplicates are safe because the handler replays the event log (`dist/index.js:98-106`; `node_modules/.bun/@workflow+world@5.2.0/node_modules/@workflow/world/dist/recovery.js:2-6`).
- Connections: each server pool has `WORKFLOW_WORKER_CONCURRENCY + 12` connections (default 22) (`apps/server/src/main.ts:22-25`; `apps/server/src/config.ts:63`). Four replicas reach 88 of Postgres's default 100 before Graphile's own listener and any operator session `[INFERENCE: default max_connections not read here]`.
- `getDeploymentId()` always returns `'postgres'` (`queue.js:351-353`) and the approval workflow id has no content hash (`apps/server/.well-known/workflow/v1/manifest.json:84-87`, generated). Runs are not pinned to a bundle version: during a rolling upgrade an old and a new replica can replay the same run with different workflow code `[INFERENCE]`. On one machine this already happens across an upgrade restart, but never concurrently.

**7.2 Workflow delivery listener.** The server registers an in-process handler for the one queue prefix the runtime uses (`apps/server/src/execution/index.ts:114-121`; `queue.js:539-549`), and the only prefix in `@workflow/core` 5.5.0's runtime is `__wkf_workflow_` `[source-read: grep of node_modules/.bun/@workflow+core@5.5.0+623ef00d5f922419]`. HTTP delivery to `WORKFLOW_LOCAL_BASE_URL` is only a fallback (`queue.js:421-422`; `apps/server/src/execution/index.ts:32-36`). So a replica never needs to reach another replica's delivery routes, and keeping them on loopback costs nothing for replicas.

**7.3 Key cache and shred delay.** Each replica caches independently. A shred evicts the local cache only (`data-key-store.ts:264-266`), so other replicas can keep using the key for up to 60 s. `NOTIFY` is transactional in Postgres and the server already holds a pool, so a `os_keys_shred` notification with a listener that evicts would make the delay short, with the TTL as the bound when a notification is missed during a reconnect `[INFERENCE: design]`.

**7.4 Sessions and ceremonies.** Sessions are rows with only the cookie's SHA-256 stored (`docs/threat-model.md:31-33`); WebAuthn ceremonies are rows consumed by a conditional `UPDATE ... RETURNING` (`apps/server/src/identity/ceremonies.ts:22-57`). Both work across replicas with no sticky sessions.

**7.5 Rate limits.** Per-agent token buckets and the per-client failed-authentication list are `Map`s in one process (`apps/server/src/mcp/gateway.ts:388-448`). With N replicas behind a balancer the effective limit is up to N times higher. The client key is the last `X-Forwarded-For` entry (`gateway.ts:398-399`), which is right behind the bundled Caddy and wrong behind a longer proxy chain such as a cloud load balancer in front of an ingress controller `[INFERENCE]`.

**7.6 Setup token.** Every boot with no owner mints a token and overwrites the stored hash (`apps/server/src/identity/setup.ts:21-33`). With replicas starting together, only the last writer's token works and the operator must find that replica's log. The token is also "the one secret any log line may carry" (`setup.ts:16-19`), and on a cluster logs are shipped and retained elsewhere `[INFERENCE]`.

**7.7 Migrations and sweepers.** The `os` migrations, the key table and the World's own migrations each take a session-level advisory lock (`apps/server/src/db/migrate.ts:13-50`; `data-key-store.ts:20-41`; `workflow-runtime.ts:65-92`), so concurrent boots serialize. Session-level advisory locks and `LISTEN` do not work through a transaction-mode pooler ([PgBouncer features](https://www.pgbouncer.org/features.html) lists both under session pooling only), so a pooler in front of Postgres must use session mode. The outbox sweeper runs every 3 s in every replica (`apps/server/src/execution/index.ts:124-132`); its writes are conditional and starting a run is serialized under `pg_advisory_xact_lock('run:<id>')` (`apps/server/src/execution/approvals.ts:198-210`), so N sweepers are N times the polling, not a correctness problem.

**7.8 Keyring rotation.** `rotate-keyring.mjs add` adds a key and makes it active in one step (`deploy/init/rotate-keyring.mjs:5-9`). With replicas, a restarted replica wraps new keys under `k2` while one not yet restarted has no `k2` and fails every unwrap of those keys (fail closed, then retried). Rotation needs two phases: distribute as inactive, then activate `[INFERENCE]`. With Transit this problem disappears: any replica can decrypt any version above `min_decryption_version`.

### 8. HA Postgres

- PostgreSQL streaming replication "is asynchronous by default. If the primary server crashes then some transactions that were committed may not have been replicated to the standby server, causing data loss" ([warm standby](https://www.postgresql.org/docs/18/warm-standby.html)). With `synchronous_standby_names` set, `synchronous_commit = on` makes a commit wait for the standby's flush ([WAL settings](https://www.postgresql.org/docs/18/runtime-config-wal.html)).
- CloudNativePG (current v1.30.1, 2026-09-23) supports quorum synchronous replication (`method: any`, `number: 1`) with `dataDurability: required` (RPO 0, writes pause when no synchronous standby is available) or `preferred` ("may result in data loss if all standbys become unavailable") ([replication.md](https://github.com/cloudnative-pg/cloudnative-pg/blob/main/docs/src/replication.md), lines 130-150, 349-450).

| Shred tombstone (`data-key-store.ts:264-275`)                                        | The wrapped key comes back; the data is readable again. Old base backups and WAL archives also hold the pre-shred row.                                                                                                                                                                                           | Shred is not durable without synchronous commit. |
| Workflow events, Graphile job completion                                             | Deliveries replay; steps are idempotent.                                                                                                                                                                                                                                                                         | Safe.                                            |
| Ceremony consumption (`ceremonies.ts:42-57`)                                         | A captured sign-in assertion could be accepted once more within 5 minutes. Approvals are unaffected (the signer's own nonce).                                                                                                                                                                                    | Minor.                                           |
| Anything in the signer                                                               | Not in Postgres.                                                                                                                                                                                                                                                                                                 | Unaffected.                                      |

Other requirements: the server must use the primary only (CloudNativePG's `-rw` service), because ceremonies and nonce reservations need read-your-writes; `LISTEN` connections must reconnect after failover, which Graphile's 500 ms polling covers for job pickup (`queue.js:1159`), while the World's run-status and stream listeners are unverified `[INFERENCE]`.

### 9. Kubernetes

1. **Secrets.** "Kubernetes Secrets are, by default, stored unencrypted in the API server's underlying data store" ([Secrets](https://kubernetes.io/docs/concepts/configuration/secret/)). Anyone who can read Secrets in the signer's namespace, and every cluster administrator, holds the signer's `token-key` and `vault-passphrase`, that is, the wallets (`docs/threat-model.md:145-155`).
2. **NetworkPolicy.** "Creating a NetworkPolicy resource without a controller that implements it will have no effect" ([Network Policies](https://kubernetes.io/docs/concepts/services-networking/network-policies/)). Policies control connections, not names: CoreDNS answers for every Service, so the v0.1 gate that agents "cannot resolve" the server is replaced by "cannot reach", or DNS egress must be denied and the gateway address supplied by Service environment variables `[INFERENCE]`.
3. **Loopback.** "Pods cannot currently block localhost" (same page), and containers in a pod "can communicate with one another using localhost" ([Pods](https://kubernetes.io/docs/concepts/workloads/pods/)). An injected service-mesh sidecar in the server pod could reach the unauthenticated Workflow delivery listener `[INFERENCE]`.
4. **Signer volume.** `ReadWriteOnce` is per node; `ReadWriteOncePod` ("mounted as read-write by a single Pod") is stable since Kubernetes v1.29 ([Persistent Volumes](https://kubernetes.io/docs/concepts/storage/persistent-volumes/)). Only `ReadWriteOncePod` on local block storage keeps one signer process per SQLite file.
5. **Root of trust.** "access to the signer's host is the root of trust in this design" (`deploy/README.md:110-111`). In a cluster, that host is every node that can schedule the signer pod plus the control plane of the cluster. Running the signer outside the cluster that runs the control plane keeps the v0.1 property `[INFERENCE]`.

The Compose networks (`compose.yaml:177-185`, `deploy/README.md:40-48`) map to policies as follows `[INFERENCE: design]`:

| Compose rule                                                           | NetworkPolicy equivalent                                                                                                             |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `agents` internal: agents reach `agent-gateway` only                   | Namespace `os-agents`, default deny; agent pods egress only to gateway pods on 80; no DNS.                                           |
| `agent-gateway` on `agents` and `control`                              | Gateway pods in `os-agents`, egress only to server pods in `os` on 3000.                                                             |
| `signing` internal: only server reaches signer; signer has no outbound | Signer egress: none. Signer ingress: server pods only, 8787 (in-cluster), or server egress to the external signer's `/32` (outside). |
| `control`: Caddy and gateway to server, server to Postgres             | Server ingress from edge and gateway pods; Postgres ingress from server pods, the other instances and the CloudNativePG operator.    |
| `chain`: server to RPC                                                 | Server egress 443 to RPC hosts (or the in-cluster anvil in CI).                                                                      |

### 10. Which step improves security

- Every v0.1 guarantee against a compromised control plane assumes the signer is not reachable by that compromise (`specs/agent-workspaces-v0.1.md:243-248`). On one machine, root on the machine is the signer host (`docs/threat-model.md:216-218`).
- Splitting the signer onto a host with different administrators turns "control-plane host root" from "all funds" into the "code execution in the control plane" row: misleading cards, pause, revoke, reading sealed content, but no passkey assertion, no cap breach, no reuse, no approver enrollment (the CLI is on the signer host, `apps/signer/src/admin.ts:17`).
- A key provider moves the keyring off the control host and gives revocation and an audit log of key use. It protects content confidentiality (asset 3), never funds: the signer does not use the keyring (`apps/signer/src/config.ts:7-19`).
- Replicas, HA Postgres and Kubernetes protect availability (asset 5) only.

### 12. A correction to the reference conversation

The reference says "Docker Compose with no hosted services required. The same manifests can later target Kubernetes" (`docs/references/chatgpt-combine-encryption-approval-ux.md:1068-1069`). Compose files are not Kubernetes manifests, and three Compose properties have no direct Kubernetes form (findings 9.2, 9.3, 9.4). Kubernetes needs its own manifests and its own isolation gate.

## Options compared

Which direction goes first:

| Option                                                          | Security gain                                         | Availability gain                     | Cost                                                            | CI-provable             |
| --------------------------------------------------------------- | ----------------------------------------------------- | ------------------------------------- | --------------------------------------------------------------- | ----------------------- |
| A. Signer on its own host (Compose on two machines, mutual TLS) | Yes: the only one                                     | None                                  | Small: TLS options, split `init`, two Compose files, one CI job | Transport and placement |
| B. OpenBao Transit key provider                                 | Content only, plus revocation and audit               | None; adds a dependency that can fail | Medium: provider, composite migration, CI service               | Yes                     |
| C. Server replicas                                              | None                                                  | Yes for the control plane             | Medium: five fixes (finding 7)                                  | Yes                     |
| D. Kubernetes manifests                                         | Negative if the signer is in the cluster              | Enables C and E                       | Large: manifests, policies, e2e driver, kind job                | Yes, on kind            |
| E. HA Postgres (CloudNativePG)                                  | None (synchronous commit keeps the audit chain whole) | Yes                                   | Large, needs D                                                  | Yes, on kind            |

## Recommendation

This is a recommendation, not a decision.

1. **Split the signer onto its own host first**, with mutual TLS in the signer itself (self-signed certificates, each side trusting exactly the other's), a per-domain `init`, and a CI job that runs the release gates across two Compose projects. It is the only step that changes what a compromised control-plane host can do.
2. **Add the restore fence in the same release.** Any move of the signer between hosts, any restore and any future standby depends on it, and it also fixes the stale-backup case on one machine.
3. **Then OpenBao Transit as the first non-file key provider**, behind an interface with `ready()` and versioned KEK ids, with a composite provider for migrating from the file keyring. Leave AWS and Google KMS for a later ticket; the interface is the contract.
4. **Then make the server replica-safe** (shared rate limits, single setup token, shred notification, two-phase file-keyring rotation, a guard against mixed workflow bundles) and prove two replicas in the existing Compose stack job.
5. **Then Kustomize manifests for the control plane, proven on kind v0.33.0** with NetworkPolicies, an agent namespace with no DNS, no sidecar injection in the server pod, and the signer outside the cluster in production (in-cluster only for CI).
6. **Then CloudNativePG with `dataDurability: required` and three instances**, with a failover gate on kind. Keep the signer single; do not replicate it.

## Limits

- Nothing here was run. Latency, connection counts, backoff after an outage, LISTEN reconnects and failover timing are read from code or documentation, or inferred.
- The Workflow and World behaviour is from the installed `workflow` 5.5.0, `@workflow/core` 5.5.0, `@workflow/world` 5.2.0 and `@workflow/world-postgres` 5.2.0 packages under `node_modules/.bun/`. A later release may change the queue, the deployment id or the lease policy.
- OpenBao facts are from its 2.7.x documentation, not from running OpenBao. AWS and Google KMS facts are from their documentation pages on 2026-11-14.
- The restore-fence argument depends on `CLOCK_SKEW_SECONDS = 30` and on the signer's clock; a signer host whose clock runs backwards across a restore weakens it.
- Separate administration of two hosts is an organisational property. No test can show it.
