# Approval notifications outside the inbox

## Question

> v0.1 has the inbox and an optional webhook (`NOTIFY_WEBHOOK_URL`, the approval outbox). Which channels are worth building for a self-hosted product (Web Push, email, chat adapters such as Telegram, Slack, Discord, ntfy), what may a notification contain without leaking sealed content, and how does a notification link lead to an approval without becoming a phishing path?

## Answer

- Build two channels into the control plane: **Web Push** to the installed web app, and the existing **webhook**, made reliable (a durable outbox with retries and dedupe) and signed. Everything else (ntfy, Telegram, Slack, Discord, email) is an optional sidecar that consumes the webhook and holds its own third-party credentials. The control plane never holds a chat token or an SMTP password.
- A notification says that something waits and where. It never carries sealed content: no amount, recipient, calldata, memo, policy, or simulation result. Default content is a count ("1 approval waiting"). A per-workspace setting may add the request kind, the workspace name and the requester's name. Amount and recipient stay on the approval page only.
- A notification link is a plain path on `PUBLIC_ORIGIN` (`/w/<workspaceId>/approvals/<approvalId>`). It carries no token and creates no session. The page needs a signed-in session, and approving needs a passkey assertion that the browser binds to the RP ID, so a lookalike link cannot obtain an approval. The signer still verifies that assertion itself; notifications never touch the signer.
- Web Push does go through a browser vendor's push service (Google, Mozilla or Apple). Payloads are end-to-end encrypted, but that service sees the subscription, timing and size. So Web Push stays **off unless the operator turns it on**, and "nothing hosted is required" still holds because no channel outside the inbox is required.

## Findings

### F1. What v0.1 sends today

1. The webhook is a single fire-and-forget `POST` with body `{ event: "approval.opened", approvalId, workspaceId, kind }`, a 5-second timeout and no retry. A failure is logged as `approval webhook failed` with the approval id and dropped. **[source]** `apps/server/src/execution/approvals.ts:738-750`.
2. It is sent after the approval row is committed and after `startRun`, outside the transaction. A process that dies between the commit (`approvals.ts:130-155`) and `#notify` (`approvals.ts:158`) never sends it, and nothing sends it later: `recoverOrphan` (`approvals.ts:704-708`) starts the workflow but does not notify. **[source]** for the call order; **[INFERENCE]** for the lost-notification consequence.
3. The request is not signed. The receiver cannot tell the control plane from anyone else who learns the URL. There is no delivery id, so the receiver cannot dedupe. **[source]** `approvals.ts:742-746` (headers are only `content-type`).
4. It fires for every approval kind (`approve-intent`, `set-policy`, `add-approver`, `remove-approver`, `set-admin-threshold`, `resume-workspace`), because `open()` is the one path for all kinds. **[source]** `packages/protocol/src/envelopes.ts:36-86`; `approvals.ts:158`.
5. Nothing is sent when an approval is decided, expires, or is about to expire. **[source]** `#notify` has one caller, `approvals.ts:158` (grep of `apps/server/src`).
6. `NOTIFY_WEBHOOK_URL` is optional; an empty value means unset. **[source]** `apps/server/src/config.ts:64-72`.
7. **The "approval outbox" in the schema is not a notification outbox.** `approvals.resume_state` is the outbox that wakes the workflow after a decision; the sweeper retries rows at `needed`. **[source]** `apps/server/src/db/schema.ts:303-307`; `apps/server/src/execution/index.ts:47-110`. The webhook has no outbox. The ticket's wording ("the approval outbox") describes something that does not exist for notifications.
8. The sweeper runs every 3 seconds in-process. **[source]** `apps/server/src/execution/index.ts:19`, `:125-133`. A notification outbox can be drained by the same loop. **[INFERENCE]**

### F2. What is sealed and what is not

1. Sealed with the workspace key: the canonical intent (operation, recipient, amount, calldata, memo), what the approval card shows and the simulation result, `approvals.detail`, signed raw transactions, audit details. **[source]** `docs/threat-model.md:171-176`.
2. Not encrypted: identifiers, names given to workspaces, agents and wallets, roles, statuses, timestamps, hashes; wallet addresses and policies. **[source]** `docs/threat-model.md:178-179`.
3. Logs carry identifiers, codes and counts only. **[source]** `apps/server/src/log.ts:3-7`. A notification leaves the system the same way a log line does: it lands in a third party's store or in the device's notification history, and encryption at rest does not cover it. **[INFERENCE]** So the log rule is the right content rule for notifications.
4. A notification that states an amount and recipient puts sealed content into an unsealed place. For chat and email it puts it on a third party's servers in readable form (Telegram cloud chats use server-client encryption only, [telegram.org/faq](https://telegram.org/faq), "Server-client encryption is used in Cloud Chats"). **[source]** for Telegram; bot chats are cloud chats, **[INFERENCE]** (secret chats are between users' devices only, same FAQ).
5. Even end-to-end encrypted Web Push ends as text on a lock screen and in the OS notification history. **[INFERENCE]**
6. There is a second reason not to show details: a passkey proves a digest was approved, not that the person saw the right details, and a compromised control plane can show one operation and submit another. **[source]** `docs/threat-model.md:199-214`. A notification that shows an amount is one more display the control plane fully controls. It invites deciding from the notification instead of the approval page. **[INFERENCE]**

### F3. Link safety in v0.1 code

1. The session cookie is `__Host-os_session` over HTTPS, `HttpOnly`, `SameSite=Strict`, `Secure`. **[source]** `apps/server/src/identity/sessions.ts:11-16`, `:98-106`.
2. `SameSite=Strict` withholds the cookie on a cross-site top-level navigation (a link tapped in a chat app or mail client). The UI still works: the HTML shell needs no cookie (`apps/server/src/http/static.ts:58-61` serves `index.html` to any GET), and the app's own `fetch` to `/api` is same-origin, so the cookie is sent then. **[INFERENCE]** from those two facts; not run.
3. A signed-out visitor is redirected to `/login` and the target path is dropped. **[source]** `apps/web/src/router.tsx:32-33`. A notification link opened while signed out lands on the workspace list after sign-in. A return path (`?next=`) is needed and must be validated so it cannot become an open redirect. **[INFERENCE]**
4. The approval API needs a session and membership: `getApproval`, `startApproval`, `approve`, `reject` are authenticated routes. **[source]** `packages/api/src/routes.ts:250-258`; non-members get `not_found` (`apps/server/src/access.ts:10-29`).
5. The relying party is `WEBAUTHN_RP_ID` or the host of `PUBLIC_ORIGIN`, with the single allowed origin `PUBLIC_ORIGIN`. **[source]** `apps/server/src/config.ts:103-107`. The shared verifier the signer uses passes `expectedOrigin` and `expectedRPID` to SimpleWebAuthn. **[source]** `packages/protocol/src/webauthn/verify-authorization.ts:93-94`; negative tests in `specs/research/passkey-assertion-bound-to-one-approval.md`, Findings 1 ("wrong origin", "wrong rpID hash"). A lookalike domain cannot get an assertion the signer accepts. **[INFERENCE]** from WebAuthn origin binding.
6. Passkeys remove the password a phishing page would steal. What a phishing notification can still do: lead a person to a real approval page for a request they would not otherwise approve (social engineering through notification text), or to a lookalike page that imitates the product. Neither yields a signature the signer accepts for a request that does not exist; the first case is the trusted-display gap again. **[INFERENCE]**
7. An approval cannot be granted from a notification action button: `navigator.credentials.get()` needs a document and user activation, and a service worker has neither. **[INFERENCE]** from the WebAuthn and Service Worker specifications; not tested. Even so, the plan forbids action buttons that call the API.

### F4. Web Push mechanics relevant here

1. Protocol: RFC 8030 (delivery), RFC 8291 (payload encryption, `aes128gcm`), RFC 8292 (VAPID). **[source]** [RFC 8030](https://www.rfc-editor.org/rfc/rfc8030), [RFC 8291](https://www.rfc-editor.org/rfc/rfc8291), [RFC 8292](https://www.rfc-editor.org/rfc/rfc8292).
2. Payloads are end-to-end encrypted to keys the browser created (`p256dh`, `auth`); TLS alone does not protect content from the push service. **[source]** RFC 8030 §8.1.
3. What the push service still sees: "The timing and length of communication cannot be hidden from the push service ... the push service will see which application server is talking to which user agent and the subscription that is used." Length leaks unless padded. **[source]** RFC 8291 §7. Header fields (TTL, Urgency, Topic) are not protected; Topic "might be used to aid traffic analysis". **[source]** RFC 8030 §8.1, RFC 8291 §7.
4. Payload limit: a push service need not accept more than 4096 octets, which leaves at most 3993 octets of plaintext. **[source]** RFC 8291 §4.
5. Topic replaces an undelivered message with the same topic; at most 32 base64url characters. **[source]** RFC 8030 §5.4. This collapses a reminder onto its first notification while the device is offline.
6. VAPID: the JWT `exp` must be at most 24 hours ahead; `sub` should be a `mailto:` or `https:` URI and is visible to the push service. **[source]** RFC 8292 §2 (lines on "exp" and "sub"). A subscription created with `applicationServerKey` is bound to that key, so pushing needs the VAPID private key, not only the endpoint. **[source]** RFC 8292 §4.
7. Which third party: Chrome and Edge use their vendor's service (for Chrome, Firebase Cloud Messaging), Firefox uses Mozilla's, Safari and iOS use Apple's (`*.push.apple.com`); no Apple Developer membership is needed. **[source]** for Apple: [WebKit, Web Push for Web Apps on iOS and iPadOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/). **[INFERENCE]** for Chrome and Firefox (common knowledge, not re-read for this report). The operator cannot choose or self-host the push service for a given browser. **[INFERENCE]**
8. iOS and iPadOS 16.4 or later: Web Push only for a web app added to the Home Screen, with a manifest whose `display` is `standalone` or `fullscreen`; permission must be requested in response to a direct user action. **[source]** WebKit post above.
9. Declarative Web Push (iOS and iPadOS 18.4, macOS 15.5): a JSON payload `{ "web_push": 8030, "notification": { "title", "body", "navigate", ... } }` is displayed without a service worker; a service worker may replace it; `window.pushManager` exists. WebKit revokes subscriptions whose service worker fails to show a notification for an imperative push. **[source]** [WebKit, Meet Declarative Web Push](https://webkit.org/blog/16535/meet-declarative-web-push/). Sending the declarative format always is backwards compatible: older browsers hand it to the service worker. **[source]** same post, "A note on backwards compatibility".
10. The v0.1 UI has no web app manifest and no service worker. **[source]** `apps/web/public/` holds only `favicon.svg`; `apps/web/index.html` has no manifest link. The static server already maps `.webmanifest` to `application/manifest+json` and serves non-`/assets/` files with `cache-control: no-cache`. **[source]** `apps/server/src/http/static.ts:13`, `:53`.
11. CSP: `default-src 'none'; script-src 'self'; ... connect-src 'self'; manifest-src 'self'` and no `worker-src`. **[source]** `packages/api/src/csp.ts:11-23`. In CSP Level 3, `worker-src` falls back to `child-src`, then `script-src`, so a same-origin `/sw.js` is allowed with no CSP change. **[INFERENCE]** from the CSP3 specification fallback list; not run in a browser. The service worker's own fetches are governed by the CSP on the `/sw.js` response, which is the same header. Subscribing does not issue a page `fetch`, so `connect-src 'self'` does not block it. **[INFERENCE]**
12. Implementation options for sending: the npm package `web-push` is at 4.0.0 (released 2026-11-10, ESM rewrite), licence **MPL-2.0**, dependencies `http_ece` 1.2.1, `jws`, `asn1.js`, `https-proxy-agent`. **[source]** `https://registry.npmjs.org/web-push` (dist-tags, versions["4.0.0"]); [releases](https://github.com/web-push-libs/web-push/releases). Node 26 (the server runtime, `apps/server/Dockerfile:36,57`) has WebCrypto ECDH P-256, HKDF, AES-GCM and ECDSA P-256, enough to implement RFC 8291 and RFC 8292 directly; RFC 8291 Appendix A gives intermediate values to test against. **[source]** for the Dockerfile and RFC appendix; **[INFERENCE]** that the WebCrypto set suffices.

### F6. Where "nothing hosted is required" stands

The v0.1 property is "Postgres, the control plane, the signer and a reverse proxy, all in one Compose file. No Vercel account, no cloud KMS, no third-party approval service." **[source]** `specs/agent-workspaces-v0.1.md:39-41`. Web Push needs no account but does depend on a vendor service the operator does not run. **[INFERENCE]** The property survives if every notification channel is optional and off by default, and the docs name the third party per channel. The control plane already reaches the internet on the `control` network (only `signing` and `agents` are `internal: true`), so outbound push needs no network change. **[source]** `compose.yaml:177-184`, `deploy/README.md:46-48`.

## Options compared

### Channels

| Option                                                            | What ships                                                                                      | For                                                                                     | Against                                                                                                       |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| A. Webhook only, made reliable                                    | Outbox, retries, signature                                                                      | Smallest; no third party by default                                                     | Every operator writes a bridge; phones get nothing out of the box                                             |
| **B. Web Push + reliable webhook built in; adapters as sidecars** | A, plus manifest, service worker, VAPID, subscriptions, preferences; one example sidecar (ntfy) | Works on the phone people already approve on; chat tokens stay out of the control plane | Vendor push services see metadata; iOS needs Home Screen install                                              |
| C. Built-in adapters (Telegram, Slack, Discord, email)            | B plus adapter code and secrets in the server                                                   | One place to configure                                                                  | Third-party credentials in the most exposed process; more personal data; more code in the trusted UI's origin |

### Content

| Level                 | Shows                                                                  | Risk                                                                                                                                      |
| --------------------- | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **`count` (default)** | "1 approval waiting" and the link                                      | Least. Leaks only that something waits, and when.                                                                                         |
| `summary`             | Adds kind ("Payment", "Policy change"), workspace name, requester name | Names are already unencrypted (F2.2) but leave the system; a requester name is chosen by people, so it can carry social-engineering text. |
| `details`             | Adds amount and recipient                                              | Puts sealed content in OS history or third-party stores (F2.4, F2.5); another untrusted display (F2.6). Not recommended.                  |

### Link

| Option                                                                  | Phishing exposure                                                                                                               |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **Path-only link on `PUBLIC_ORIGIN`, session plus passkey on the page** | A lookalike gets no usable assertion (F3.5). Notification text can still nudge (F3.6).                                          |
| Link with a one-time approval or sign-in token                          | The token becomes the capability; anyone who sees the notification (lock screen, chat history, mail server) holds it. Rejected. |
| No link, "open the app" text only                                       | Safest against lookalike links; worse to use. Reasonable for email and chat sidecars.                                           |

## Recommendation

This is a recommendation, not a decision.

1. **Option B.** Built in: Web Push and a reliable, signed webhook. Sidecars for everything else, starting with an ntfy example. No email in this step.
2. **Content level `count` by default; `summary` allowed per workspace by an owner; never amount, recipient, calldata, memo, policy contents, or simulation output on any channel.** Reason: notifications are a plaintext channel like logs (F2.3), and the approval page is the one place to decide (F2.6).
3. **Links are path-only on `PUBLIC_ORIGIN`, built by the server from ids, never from request input.** The page requires a session; sign-in returns to a validated same-origin path. No tokens, no magic links, no notification action that calls the API.
4. **Durable outbox.** Rows written in the same transaction as the approval; delivered by the existing sweeper with backoff; dropped when the approval leaves `pending`; one reminder before expiry; Topic and `tag` set from the approval so repeats collapse; webhook body carries a delivery id and an HMAC signature.
5. **Web Push off by default**, enabled by `WEB_PUSH_VAPID_KEY_FILE`; the docs name the vendor push services as the third party. Implement RFC 8291/8292 in-house with Node WebCrypto rather than adding `web-push` 4.0.0 (MPL-2.0, four days old): roughly two hundred lines with the RFC's own test vectors. This is an owner decision (dependency and licence policy).
6. **Per-person preferences** (Web Push on or off per workspace, reminders on or off, quiet hours with a time zone); deliveries in quiet hours wait until the window ends and are dropped if the approval has expired by then.

None of this changes the signer or the approval protocol. The signer still decides whether a person approved and signs only what was approved; a notification is never an input to that decision. **[INFERENCE]**

## Limits

- Nothing was run. No browser registered `/sw.js` under the production CSP; the CSP fallback in F4.11 is from the specification, not observed.
- Behaviour of Chrome's and Firefox's push services (retention, rate limits, what they log) was not read from their documentation for this report.
- Whether a declarative push `navigate` URL must be same-origin was not confirmed in the specification draft ([w3c/push-api#385](https://github.com/w3c/push-api/pull/385)); the plan validates it in the service worker for the imperative path and states the gap for the declarative path.
- Slack and Discord webhook behaviour is stated from general knowledge, not re-read.
- The `SameSite=Strict` reasoning in F3.2 is not tested from a chat app's in-app browser, which may hold its own cookie jar and so have no session at all.
